# Hermes Agent v0.21 Kanban Swarm 深度解析——面向 AI 开源者的协作拓扑

## 从一条微信消息说起

凌晨三点，微信嗖地一声弹出来："写一篇 2000 字，主题是 Hermes Agent v0.21 的 Kanban Swarm。"

以前的流程是：你接到消息，打开几个标签页查资料，写大纲，找图，润色，发博客——每一步都卡在同一个上下文里，你疲于切换角色。写作者变成了调度员，调度员又亲力亲为，品质就靠一个人的注意力跨度支撑。但 Hermes Agent v0.21 设计了一个不同的结局：一条消息进来，触发"Kanban Swarm 一键启动协作拓扑"，Orchestrator 拆解任务，Researcher、Writer、Reviewer、Publisher 五个 Profile 依次执行，最后文章发布到 GitHub。这并不是导入了一个"多 Agent 框架"，而是把现有的 Hermes Profile 体系通过 Kanban 组织起来，让工作流具有了拓扑结构。

为什么重要：当你的产品面向 AI 开源者时，他们不只想看 API，他们想理解工作流的组织逻辑——任务怎么被分解、Profile 怎么通信、黑板怎么避免熵增。理解 Swarm，就是理解这个产品的协作骨架。

## 五个 Profile 的串行故事

可观测的协作拓扑第一步，就是五个 Profile 的串行故事：

- **Orchestrator**：接收微信消息，产出一张"Swarm 拓扑规划卡"——定义目标、决定分工、把根任务留作共享黑板。
- **Researcher**：调研主题，收集资料和参考链接。
- **Writer**：基于调研成果，独立撰写 2000 字文章。
- **Reviewer**：检查语法、结构、事实引用，把文章推向更稳的质量。
- **Publisher**：发布到 GitHub。

这是 Swarm protocol 里写明的默认故事。五个 Profile 依次执行：Orchestrator → Researcher → Writer → Reviewer → Publisher。其中，Orchestrator 是拓扑的入口，Writer 是本文案例中的当前角色。整个过程在 Kanban 任务系统上运行——每个 Profile 对应一个工人（worker），每个工人对应至少一张卡。

为什么重要：开源者往往已有自己的多 Agent 实验，但多数实验缺乏"能观测的中间状态"。Swarm 把中间状态暴露成了卡片和事件，让你能看到一条消息如何变成一篇文章，而不仅仅是看到最终结果。

## Swarm 拓扑：根、工人、孩子卡

v0.21 的 Swarm 拓扑结构可从根任务 t_0199c7a1 看到完整图景。根任务是一个规划/黑板卡，创建后立刻完成，留作共享黑板和审计锚点。它的孩子卡是三个 worker：t_4290b5a6、t_69d3d217 和 t_0e29e80f。本次实验共 3 个 worker，并不等于只有 3 个 Profile 参与——Worker 是运行单元，Profile 才是扮演的角色。一个拓扑中可以有多个 Researcher 卡，也可以有多个 Reviewer 卡，视任务规模与并行策略而定。

关于拓扑细节，根卡通过结构化评论写下了键值对：

    [swarm:blackboard] {"key": "topology", "value": {"goal": "...", "root_id": "...", "synthesizer_id": "...", "verifier_id": "...", "worker_ids": [...]}}

这一行很关键——它把 Swarm 的元信息显式写进黑板，让任何工人都能读取全局形态，而不依赖隐式约定。为什么重要：分布式工作流里最容易失效的地方，就是"大家以为我已经知道你的计划"。显式黑板把计划变成了数据，冲突可以被检测，责任可以被追踪。

## 工作流转移：todo → ready → blocked → done

Swarm 的核心机制不是消息传递，而是状态流动。Kanban 工作流的基本形态：

- **todo**：工人尚未开始。
- **ready**：工人可以执行——通常因为父卡已完成。
- **blocked**：遇到外部依赖或人工输入，暂停。
- **done**：工人完成了手头的契约，并留下手递手的元信息。

这一模型里，一个 worker 的卡从 todo 到 ready，是由父卡的完成驱动的。比如当前的 Writer 卡 t_0e29e80f，就是在 Orchestrator 完成根规划之后获得执行权的。另一方面，blocked 状态不是失败——它只是表示"我这里缺一个外部决策"。对于开源者来说，这种状态语义特别有用：你可以把 Swarm 接入真实世界的等待（比如等待人工确认、等待远程 API 返回、等待子任务产出），而不把它们伪装成成功或错误。

此外，Swarm protocol 还提到"Profile 咨询"和"任务净化流转"。Profile 咨询意味着，在某个决策影响多个工人时，不要各自瞎猜——把决策写进黑板或卡片正文，然后每个工人读取同一份决策。任务净化流转意味着，每张卡被完成时都附带机器可读的摘要和 metadata，而不是"我搞定了"这种自然语言模糊句。前者防止分歧，后者防止不可复现的历史。

## 事件与运行时锚点

每个卡的生命周期都带有一串事件——created、promoted、claimed、spawned、heartbeat、commented、completed。以当前 Writer 卡为例，它先被创建，随后被提升，接着被 claimed（锁住），再被 spawned（新运行开始）。运行时锚点（run_id, expires, pid）让工具调用看起来像是一个运行中的工人，而不仅是一条静态记录。

为什么重要：调试分布式系统时，最怕"发生了什么我看不到"。如果你的 Swarm 多次运行，事件流就是复盘的原材料——你能回答"卡到底有没有被正确锁住""worker 是否在正确的时间点开始"。对面向 AI 开源者而言，这是把运维透明度直接嵌入到工作流产品里的做法。

## 手动触发的方式

本文写作案例是由 Orchestrator 触发的，但开源者最关心的是：我怎么自己触发一次 Swarm？

Hermes Agent v0.21 的 Swarm 是通过 Kanban 板驱动的。从用户侧来看，一个典型的手动入口是：

    hermes swarm spawn --board blog --topic "Hermes Agent v0.21 Kanban Swarm 深度解析"

实际命令会随着版本演进而调整，但思路是不变的：指定板和主题，由 Orchestrator 工人创建根卡，根卡写下拓扑元信息，随后子 worker 卡接力开始。每一步都在 Kanban 事件流里。

Swarm 黑板使用结构化评论来更新状态，例如本次实验的拓扑评论，就是由默认工人写下的。这说明黑板不是隐藏的后端表，是一个明确可读/可写的协作通道。

为什么重要：如果你在 GitHub 上维护一个 AI 项目，Swarm 的可观测性和可触发性意味着你的贡献者可以复现协作实验、插入自定义 worker、验证整个流是否像文档写的那样运行。

## 边界案例：研究者尚未完成时的写作

本文面临了一个有意思的边界情况：Writer 卡 t_0e29e80f 当前在运行，但它的兄弟研究者卡 t_4290b5a6 与 t_69d3d217 仍处在 todo。这是 Swarm 的实验现场——Writer 不得不在研究成果尚未交付时，先行独立写作。

在 Swarm protocol 里，这并不表示工作流出了问题，而是展示了一种现实可能：工人之间的等待不总是同步的，有时你需要在缺少兄弟输入的情况下做最高质量的单点输出，然后把输出留在黑板上供后续校验。后续 Reviewer 卡 t_f9ffde04 会审查所有 worker 的输出，并决定是否 gate 通过——只有证据充分才写 metadata {"gate": "pass"}，否则它会 block 并指出缺失的具体工作。

为什么重要：对 AI 开源者而言，这种把"不确定性纳入工作流设计"的思路非常实用。不是所有并行工作都能完美同步；更健壮的系统会显式表达这种不确定性，而不是假装同步总是成立。

## 合成器与校验器：Swarm 的质量门

拓扑里还出现了 synthesizer_id 和 verifier_id——分别指向合成器卡 t_2ef54727 和校验器卡 t_f9ffde04。它们不在 worker 同步执行线上，而是在所有 worker 产出之后工作。合成器负责把多个 worker 的输出合成为最终成果，校验器负责在发布前做质量检查。

本次实验中，当前 Writer 卡已经有一个孩子卡 t_f9ffde04（Reviewer）作为其 downstream。合并后的合成器/校验器设计意味着 Swarm 不只是"多个工人轮流干", 而是有明确的产出合并和质量把关阶段。这也是为什么"Swarm topology planned"本身就可以作为一次实验的审计锚点——它记录了谁该在什么时候产生什么。

为什么重要：很多多 Agent 演示止步于"他们都输出了", 却回避了怎么合并、怎么确认合并后的产出是一致的。Swarm 内建了这个问题的答案：有合成器，有校验器，有黑板，有门控元数据。

## 结语：把协作变成可读的结构

Hermes Agent v0.21 的 Kanban Swarm 不是某个巨型新功能，而是一套协作语法：Profile 体系 + Kanban 任务流 + 显式黑板 + 状态流转 + 事件可观测性。它让一条微信消息可以被拆解为多个工人卡，转移状态、交叉检查、最后发布。

对于 AI 开源者而言，Swarm 的意义在于两个层面。第一层是产品层：你可以使用它来驱动文档编写、提案起草、实验报告生成这样的任务流。第二层是设计层：Swarm 向你展示了如何组织可复现的多 Profile 协作——明确的拓扑、显式的元信息、黑板化的约定、状态语义化的阻塞与完成。

如果你在尝试构建自己的 AI 工作流，不妨先回答一个问题：你的协作今天是隐式约定驱动的，还是显式结构驱动的？Swarm 选择了后者，并把每一次选择都留在了可以看见的卡片与事件里。
